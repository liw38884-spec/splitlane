# SplitLane threat model

This document captures the security assumptions for the current SplitLane implementation.

## Assets

- USDC held by participant wallets
- The recipient's expected payment
- Tab metadata and settlement state
- Proof evidence generated by the Attestcoin lane

## Threats and controls

| Threat | Impact | Existing control |
| --- | --- | --- |
| Reentrancy during settlement | Double payment or corrupted state | `ReentrancyGuard` wraps state-changing contract functions |
| Contract custody risk | Funds trapped in the contract | The contract transfers USDC directly to the recipient and never exposes a withdrawal path |
| Fake recipient or wrong contract address | Settlement goes to the wrong destination | The frontend and Attestcoin lane both bind transactions to configured contract addresses |
| Wrong chain submission | Proof lane accepts unsupported source transactions | Attestcoin rejects Base Sepolia and only accepts Ethereum Sepolia |
| Reused share payment | Duplicate payout by the same participant | Each share is marked paid before the transfer completes and the transfer is guarded by `SafeERC20` |
| Self-payment volume | A recipient records settlement without moving value | Contract creation rejects the recipient as a participant |
| Malformed ERC-20 behavior | Silent transfer failures | `SafeERC20` reverts when the token returns false or behaves unexpectedly |
| Native currency injection | Unexpected ETH or MATIC custody | The contract has no payable path and rejects native transfers |
| Unauthorized tab closure | Payment window closed by the wrong actor | Only the tab recipient can close an open tab |
| Demo-mode confusion | A user mistakes demo data for live settlement | The UI labels demo data explicitly and separates it from live contract state |
| Invalid proof submission | False verification evidence | The lane verifies the source transaction, block inclusion, contract address, and function selector before emitting evidence |
| Compromised proof builder | Proof bytes describe a different transaction | The lane rebuilds the SDK EVM-v1 encoding from the inspected transaction and receipt and requires byte equality |

## Assumptions

- The configured USDC address is the official Circle token address for the target chain.
- Wallets sign only transactions they intend to send.
- Chain RPC endpoints return honest-enough data for the supported testnets.
- CC3 proof-builder and BlockProver services behave according to the `@gluwa/usc-sdk` contract.

## Out of scope

- Mainnet deployment risk
- Exchange or bridge risk
- Private-key storage inside the repository
- Social engineering against users
- DoraHacks eligibility review

## Operational notes

- Base Sepolia is valid for SplitLane app usage, but not for Attestcoin proof generation.
- Ethereum Sepolia is the only source chain accepted by the proof lane.
- The proof lane is fail-closed: unsupported chain, wrong contract, wrong selector, or missing signer all stop the workflow.
